# PMIP Integration Consistency and Edge-Case Review

## 1. Purpose

The purpose of this review is to confirm that PMIP intelligence integration behaves consistently when the data contains unusual, incomplete or potentially ambiguous situations.

The review focuses on areas where integration errors could cause the public dashboard to display outdated, duplicated, missing or misleading intelligence.

The main areas reviewed are:

```text
run_id handling
missing intelligence
canonical identifiers
source-only artist records
releases containing multiple tracks
empty intelligence tables
```

The review checks whether these cases are handled consistently across:

```text
PMIP Database
        ↓
Backend Repository
        ↓
Backend Service
        ↓
Backend Controller
        ↓
REST API
        ↓
React Frontend
```

The goal is to confirm that edge cases do not break the application and that the dashboard continues to represent the underlying PMIP intelligence correctly.


## 2. `run_id` Handling Review

### Purpose

The purpose of this review is to confirm that PMIP serves intelligence from the correct and most recent analytical run rather than mixing results from different generations of the intelligence pipelines.

PMIP uses:

```text
run_id
```

to associate generated intelligence records with a particular execution of an analytical component.

This is important because the same intelligence table may contain results from several historical runs.

Without correct `run_id` filtering, the dashboard could accidentally display:

```text
old intelligence
duplicate intelligence
mixed results from different runs
```

### General Backend Pattern

The main intelligence repository consistently uses the:

```text
intelligence_runs
```

table to identify the latest run for a specific intelligence component.

The common pattern is:

```sql
SELECT MAX(run_id)
FROM intelligence_runs
WHERE component_name = '...'
```

The result table is then filtered using that `run_id`.

Conceptually:

```text
Intelligence table contains several runs
        ↓
Find latest run_id for the required component
        ↓
Return only rows belonging to that run
        ↓
Serve results through the API
```

### Geographic Intelligence

Geographic intelligence uses:

```text
component_name = 'geographic_intelligence'
```

The latest-run filter is applied to:

```text
country_geographic_intelligence
artist_geographic_intelligence
track_geographic_intelligence
```

The collection count queries use the same latest-run rule.

This ensures that pagination totals and returned results refer to the same geographic intelligence generation.

### Market Growth Intelligence

Market-growth intelligence uses:

```text
component_name = 'market_growth_intelligence'
```

The latest-run filter is applied across the related intelligence tables, including:

```text
country_market_growth
artist_market_growth
track_market_growth
artist_growth_intelligence
track_growth_intelligence
track_market_movements
```

Individual artist growth lookups also use the latest market-growth run.

This keeps market-growth scores, final growth intelligence and movement outputs associated with the same current analytical generation.

### Artist Momentum

Artist momentum uses:

```text
component_name = 'artist_momentum_scoring'
```

Both:

```text
collection retrieval
individual artist retrieval
```

filter to the latest momentum run.

This prevents an artist profile from accidentally retrieving an older momentum result while the collection endpoint displays newer intelligence.

### Track Forecasting

Forecasting uses:

```text
component_name = 'artist_performance_forecasting'
```

Both:

```text
forecast collection retrieval
individual track forecast retrieval
```

filter to the latest forecasting run.

This ensures that the dashboard does not mix predictions generated by different forecasting executions.

### Streaming Anomaly Detection

Track anomalies and artist anomaly summaries use:

```text
component_name = 'streaming_anomaly_detection'
```

The repository filters anomaly results to the latest anomaly-detection run.

This applies to both:

```text
track-level anomaly results
artist-level anomaly summaries
```

This is important because anomaly outputs can change as new streaming observations are processed.

### Release Performance

Release-performance intelligence follows a slightly different latest-run pattern.

The release repository identifies the latest available release-performance run using:

```sql
SELECT MAX(run_id)
FROM release_performance_intelligence
```

instead of querying:

```text
intelligence_runs
```

for a component name.

The release-performance endpoint therefore retrieves performance rows belonging to the highest `run_id` currently present in:

```text
release_performance_intelligence
```

This still prevents older release-performance rows from being mixed with current results.

However, its latest-run lookup is implemented differently from the other intelligence components.

### Consistency Finding

The main PMIP intelligence repositories consistently prevent historical intelligence runs from being mixed with current dashboard results.

The current pattern can be summarised as:

```text
Geographic
→ latest geographic_intelligence run

Market Growth
→ latest market_growth_intelligence run

Momentum
→ latest artist_momentum_scoring run

Forecasting
→ latest artist_performance_forecasting run

Anomaly Detection
→ latest streaming_anomaly_detection run

Release Performance
→ highest run_id present in release_performance_intelligence
```

### Important Edge Case

The current implementation generally assumes:

```text
highest run_id
=
latest usable intelligence run
```

This works correctly when new `run_id` values are created only for valid completed intelligence imports.

However, a future automated scheduling system may introduce situations where:

```text
a new run starts
        ↓
run_id is created
        ↓
pipeline fails or imports only partial data
```

If the backend simply selects:

```sql
MAX(run_id)
```

a failed or incomplete run could potentially become the apparent latest run.

A stronger future architecture should distinguish between:

```text
started
completed
failed
partial
```

intelligence runs and allow the backend to select the:

```text
latest successful completed run
```

rather than only the highest numerical `run_id`.

### Recommended Future Improvement

When the scheduled intelligence-refresh system is introduced, `intelligence_runs` should ideally record a run status such as:

```text
started
completed
failed
partial
```

The backend could then use logic conceptually similar to:

```sql
SELECT MAX(run_id)
FROM intelligence_runs
WHERE component_name = ?
AND status = 'completed'
```

This would prevent failed future pipeline executions from replacing the latest valid public intelligence.

### `run_id` Review Result

```text
Current Status: PASS
Future Hardening Recommended: Yes
```

The current PMIP implementation consistently filters intelligence results by the latest relevant `run_id`.

No evidence was identified that the current dashboard mixes historical intelligence runs.

The main future improvement is to ensure that scheduled automation selects the latest successful run rather than assuming the largest `run_id` is always valid.

## 3. Missing Intelligence Handling Review

### Purpose

The purpose of this review is to confirm that PMIP behaves correctly when a valid artist, track or release exists but one of its intelligence results is unavailable.

This is an important edge case because analytical coverage is not guaranteed to be identical across every PMIP entity.

A valid resource should not appear broken simply because one intelligence model has no result for it.

### Current Design Principle

The current frontend separates:

```text
essential resource data
```

from:

```text
optional intelligence data
```

For example:

```text
artist profile
        +
optional momentum intelligence
        +
optional growth intelligence
```

and:

```text
release details
        +
related tracks
        +
optional release-performance intelligence
```

This means the main entity can still be displayed even when one analytical result is unavailable.

### Artist Momentum

Artist momentum is treated as optional intelligence.

A valid artist may exist in:

```text
artists
```

without having a corresponding current result in:

```text
artist_momentum_results
```

If the momentum endpoint returns no result, the frontend displays an unavailable or error state for the momentum section instead of failing the entire artist experience.

The main artist record remains valid.

### Artist Growth Intelligence

Final artist growth intelligence is also optional.

A valid artist can exist without a current result in:

```text
artist_growth_intelligence
```

The Artist Details page loads core artist information separately from growth intelligence.

Therefore:

```text
missing growth result
```

does not mean:

```text
missing artist
```

### Track Forecasting

A valid track may exist even if no forecast result is available in:

```text
forecast_results
```

The frontend treats forecasting as optional intelligence.

A missing forecast therefore results in an unavailable-intelligence state rather than incorrectly classifying the track as invalid.

### Release Performance

Release-performance intelligence is also separated from the essential release workflow.

The frontend first loads:

```text
release details
related tracks
```

and then loads:

```text
release-performance intelligence
```

separately.

This means that if:

```text
release_performance_intelligence
```

contains no matching result for the selected release, the frontend can still display the release and its tracks.

The user is shown an empty or unavailable intelligence state instead of a broken release page.

### Geographic and Market Intelligence

Collection-based geographic and market intelligence components also distinguish between:

```text
successful request with results
```

and:

```text
successful request with zero results
```

An empty collection is treated as a valid data condition.

This prevents the application from reporting an API failure when the current intelligence run simply has no matching records.

### Backend Behaviour

The backend service and controller layers distinguish between:

```text
resource not found
```

and:

```text
intelligence not found
```

where appropriate.

This distinction is important because:

```text
Artist does not exist
```

is different from:

```text
Artist exists but has no momentum result
```

The same principle applies to tracks and releases.

### Frontend Behaviour

The frontend currently supports states including:

```text
loading
successful result
unavailable intelligence
empty result
API error
backend connection error
```

This allows optional intelligence to fail independently from the main resource.

### Edge-Case Example

The intended behaviour can be represented as:

```text
Valid artist exists
        ↓
Artist profile loads
        ↓
Momentum lookup returns no result
        ↓
Momentum section shows unavailable state
        ↓
Artist profile remains visible
```

rather than:

```text
Momentum missing
        ↓
Entire artist page fails
```

### Consistency Finding

The current PMIP integration consistently treats intelligence outputs as optional where appropriate.

This is particularly important for:

```text
artist momentum
artist growth
track forecasting
release performance
```

The application does not assume that every entity must have every analytical output available.

### Missing Intelligence Review Result

```text
Current Status: PASS
```

The current integration handles missing intelligence without incorrectly invalidating the underlying artist, track or release.

This behaviour should be preserved as additional intelligence models are added to PMIP.

## 4. Canonical ID Handling Review

### Purpose

The purpose of this review is to confirm that PMIP uses canonical identifiers consistently across the database, backend API and frontend.

The main identifiers reviewed are:

```text
artist_id
track_id
release_id
country_id
```

These IDs are important because PMIP integrates intelligence generated from different source datasets.

A source record may use a label or external identifier that is different from the canonical PMIP record used by the web application.

### Canonical Identifier Principle

The current PMIP architecture separates:

```text
source identifiers / source labels
```

from:

```text
canonical PMIP identifiers
```

For example:

```text
source_artist_label
source_artist_key
source_track_id
source_country
```

may exist alongside:

```text
artist_id
track_id
country_id
```

This allows PMIP to preserve the original analytical source information while still linking matched records to stable internal entities.

### Artist IDs

Canonical artists are identified using:

```text
artist_id
```

from the:

```text
artists
```

table.

Where an intelligence record has been successfully matched to a canonical PMIP artist, repository queries join using:

```text
artist_id
```

This allows the backend to return:

```text
artist_name
```

together with the intelligence result.

Examples include:

```text
artist momentum
artist growth intelligence
artist anomaly summaries
artist geographic intelligence
artist market growth
```

### Track IDs

Canonical tracks are identified using:

```text
track_id
```

from the:

```text
tracks
```

table.

Track-based intelligence is connected using this identifier where a canonical match exists.

Examples include:

```text
forecasting
streaming anomalies
track geographic intelligence
track market growth
release performance
```

This provides a stable internal link between track intelligence and the main track record.

### Release IDs

Canonical releases are identified using:

```text
release_id
```

from the:

```text
releases
```

table.

Release-performance intelligence links to a release using:

```text
release_id
```

while each result can also contain a:

```text
track_id
```

This is important because one release may contain multiple tracks.

The combination allows PMIP to represent:

```text
one release
        ↓
many tracks
        ↓
track-level release-performance intelligence
```

### Country IDs

Canonical countries are identified using:

```text
country_id
```

from the:

```text
countries
```

table.

Country-based intelligence can therefore link to a stable PMIP country record while preserving original source values where necessary.

Examples include:

```text
country geographic intelligence
country market growth
artist market growth
track market growth
market movements
streaming observations
```

### Source Identifiers

Some intelligence records preserve source-level identifiers such as:

```text
source_artist_label
source_artist_key
source_artist_identity_key
source_track_id
source_country
source_release_id
```

These fields are useful because they allow PMIP to retain the original analytical identity even if a canonical mapping is incomplete.

This means PMIP does not need to discard valid analytical output simply because a source entity has not yet been fully matched.

### Join Strategy

The repositories use different join types depending on whether a canonical mapping is required.

For intelligence that requires a canonical entity, an:

```text
INNER JOIN
```

may be used.

For intelligence where source-only records should remain available, a:

```text
LEFT JOIN
```

is used.

This is visible in areas such as:

```text
artist geographic intelligence
artist market growth
country market growth
track market growth
market movements
```

### Frontend Handling

The frontend generally prefers the canonical display value where available.

For example:

```text
artist_name
country_name
track_name
```

When a canonical name is unavailable, some components can fall back to source-level values such as:

```text
source_artist_label
source_country
source_track_id
```

This prevents source-only analytical records from appearing blank.

### Edge-Case Risk

The main risk with canonical identifiers is that the same source entity could be:

```text
unmatched
incorrectly matched
matched to multiple canonical entities
```

If that happened, intelligence could be displayed under the wrong artist, track, release or country.

The current integration relies on the quality of the earlier identity-mapping and import stages.

### Consistency Finding

The current PMIP integration uses canonical IDs consistently across the main backend and frontend workflows.

The general pattern is:

```text
source identity preserved
        +
canonical PMIP ID when available
        ↓
backend joins canonical tables
        ↓
frontend displays canonical name
```

This provides both traceability and stable application-level identity.

### Recommended Future Improvement

As PMIP grows, identity mapping should remain auditable.

It would be useful to continue preserving:

```text
source identifier
canonical identifier
mapping confidence or mapping method
```

where available.

This would make it easier to investigate incorrect or ambiguous entity mappings later.

### Canonical ID Review Result

```text
Current Status: PASS
```

Canonical artist, track, release and country IDs are used consistently across the current PMIP integration.

Source-level identifiers are preserved where needed, reducing the risk of losing valid intelligence when canonical mapping is incomplete.

## 5. Source-Only Artist Handling Review

### Purpose

The purpose of this review is to confirm that PMIP can preserve valid intelligence for artists that appear in analytical source data but do not yet have a confirmed canonical:

```text
artist_id
```

in the main PMIP artist table.

These records are referred to as:

```text
source-only artists
```

### Why Source-Only Artists Matter

PMIP combines data from multiple music and streaming sources.

A source dataset may contain an artist name or identity that cannot immediately be matched with confidence to a canonical PMIP artist.

For example:

```text
Source Artist
        ↓
Valid streaming or market intelligence
        ↓
No confirmed canonical artist_id
```

Discarding that record would mean losing useful intelligence.

PMIP therefore preserves source-level artist identity where possible.

### Current Identity Pattern

Source-level artist information can be retained using fields such as:

```text
source_artist_label
source_artist_key
source_artist_identity_key
```

while:

```text
artist_id
```

may remain unavailable until a reliable canonical match is established.

Conceptually:

```text
Source artist identity
        ↓
Attempt canonical matching
        ↓
Match found?
   ├── Yes → attach artist_id
   └── No  → retain source-level identity
```

### Backend Handling

Some intelligence repository queries are designed so that a missing canonical artist does not automatically remove the analytical record.

Where source-only results need to remain visible, the repository can use:

```text
LEFT JOIN
```

rather than requiring a successful canonical artist match.

This allows the intelligence record to remain available even when:

```text
artist_id = NULL
```

or no matching row exists in the canonical artist table.

### Frontend Handling

Where a canonical artist name is available, PMIP should display:

```text
artist_name
```

from the canonical artist record.

Where no canonical artist exists, the interface can fall back to the preserved source identity.

The intended display logic is:

```text
canonical artist name available
        ↓
display canonical name

otherwise
        ↓
display source artist label
```

This prevents valid analytical rows from appearing blank.

### Important Separation

A source-only artist should not automatically be treated as:

```text
invalid data
```

Instead, it represents:

```text
valid analytical identity
+
incomplete canonical mapping
```

This distinction is important because identity resolution and intelligence generation are separate concerns.

### Edge-Case Risk

The main risks are:

```text
source-only artist incorrectly mapped later
duplicate source identities representing the same artist
different spelling of the same artist name
collaborations or featured artists creating ambiguous identity
```

For this reason, PMIP should avoid forcing uncertain mappings simply to populate an `artist_id`.

Preserving the source identity is safer than attaching intelligence to the wrong canonical artist.

### Consistency Finding

The PMIP integration supports the principle that analytical intelligence can remain valid even when canonical artist resolution is incomplete.

The general strategy is:

```text
preserve source identity
        ↓
attach canonical artist_id where confidently available
        ↓
retain source-only record when no safe match exists
```

This helps PMIP avoid unnecessary data loss while still protecting the integrity of canonical artist relationships.

### Recommended Future Improvement

As the platform develops, source-only artist records could be supported by a dedicated identity-resolution workflow.

For example:

```text
source-only artist detected
        ↓
added to mapping review queue
        ↓
candidate canonical matches identified
        ↓
human or automated confirmation
        ↓
artist_id assigned
```

This would allow unresolved artist identities to be reviewed without blocking intelligence generation.

### Source-Only Artist Review Result

```text
Current Status: PASS
```

The current PMIP integration can preserve useful source-level artist intelligence without requiring every record to have an immediate canonical artist match.

This reduces data loss and avoids forcing uncertain artist mappings.


## 6. Releases with Multiple Tracks Handling Review

### Purpose

The purpose of this review is to confirm that PMIP handles releases containing more than one track correctly.

This matters because a release is not always a single-track item.

A release may represent:

```text
single
EP
album
multi-track project
```

Therefore, PMIP must avoid assuming:

```text
one release = one track
```

### Current Data Relationship

The current PMIP design allows one:

```text
release_id
```

to be associated with multiple:

```text
track_id
```

values.

Conceptually:

```text
Release
   ↓
Track 1
Track 2
Track 3
...
```

This is important for release-performance intelligence because analytical results may need to be stored and displayed at track level while still belonging to the same release.

### Release Performance Structure

The:

```text
release_performance_intelligence
```

table contains release-level linkage through:

```text
release_id
```

while also retaining:

```text
track_id
```

for the individual track represented by each analytical result.

This allows PMIP to represent:

```text
one release
        ↓
multiple track-level performance records
```

without losing the relationship between the tracks and the parent release.

### Backend Handling

The release repository retrieves release-performance intelligence using the selected:

```text
release_id
```

rather than assuming only one row exists.

This means the backend can return several analytical records for the same release.

The expected behaviour is:

```text
GET release performance for release_id
        ↓
find latest valid intelligence run
        ↓
return all matching track-level rows
```

rather than:

```text
return only the first matching track
```

### Frontend Handling

The release page separates:

```text
release details
```

from:

```text
release-performance intelligence
```

The intelligence response can therefore contain multiple track-level entries belonging to the same release.

The frontend can display those results as a collection or chart rather than treating the release-performance response as a single track record.

### Example Behaviour

For a release containing three tracks:

```text
Release ID: 10

Track ID: 101
Track ID: 102
Track ID: 103
```

the expected intelligence flow is:

```text
Release 10
        ↓
Performance result for Track 101
Performance result for Track 102
Performance result for Track 103
```

All three rows should remain associated with:

```text
release_id = 10
```

### Edge-Case Risk

If the application incorrectly assumed:

```text
one release = one performance result
```

then multi-track releases could cause:

```text
missing track intelligence
incorrect aggregation
only the first track being displayed
duplicated release information
```

The current structure avoids this by keeping both:

```text
release_id
track_id
```

in the analytical relationship.

### Consistency Finding

The PMIP release-performance integration is designed to support one-to-many release-to-track relationships.

The structure can be summarised as:

```text
release_id
        ↓
multiple track_id values
        ↓
multiple release-performance intelligence rows
```

This is consistent with the underlying music-domain relationship between releases and tracks.

### Recommended Future Improvement

As the UI/UX phase develops, multi-track release intelligence should be presented clearly.

Useful presentation options could include:

```text
track-level table
track comparison chart
release-level summary
expandable track details
```

The release-level summary should remain separate from the underlying individual track-performance records.

### Releases with Multiple Tracks Review Result

```text
Current Status: PASS
```

The current PMIP data and backend structure supports releases containing multiple tracks without requiring a one-release-to-one-track assumption.

This allows track-level performance intelligence to remain correctly associated with its parent release.

## 7. Empty Intelligence Tables Handling Review

### Purpose

The purpose of this review is to confirm that PMIP behaves correctly when an intelligence table or the latest intelligence run contains no rows.

An empty intelligence result should be treated as:

```text
valid empty data
```

rather than:

```text
application failure
```

This distinction is important because some PMIP analytical components may legitimately produce no records for a particular run.

### Current Expected Behaviour

The intended integration pattern is:

```text
Database contains no matching intelligence rows
        ↓
Repository returns an empty collection
        ↓
Service passes the empty result forward
        ↓
Controller returns a successful API response
        ↓
Frontend displays an empty-state message
```

The system should not fail simply because there is currently no intelligence to display.

### Market Movements Example

Market Movements provides a real example of this edge case.

During the current PMIP integration work, the latest market-growth intelligence run contained:

```text
0 market movement rows
```

The backend endpoint still responded successfully.

The frontend then displayed the corresponding empty state rather than treating the response as a system error.

The flow was:

```text
Latest intelligence run
        ↓
No market movement records
        ↓
API returns empty collection
        ↓
Frontend shows no-data / empty-state message
```

This is the correct behaviour.

### Why This Matters

An empty result and an API failure represent two different situations.

#### Empty Result

```text
Request succeeded
Database query succeeded
No matching intelligence currently exists
```

#### API Failure

```text
Request failed
Database unavailable
Query failed
Server error occurred
```

The frontend should not present these two situations in the same way.

### Collection-Based Intelligence

This behaviour is especially important for collection endpoints such as:

```text
country geographic intelligence
artist geographic intelligence
market growth intelligence
track anomalies
artist anomaly summaries
market movements
```

These endpoints may sometimes legitimately return:

```json
[]
```

or an equivalent empty data structure.

The application should still consider the request successful.

### Individual Intelligence Lookups

Individual lookups are slightly different.

For example:

```text
momentum for one artist
forecast for one track
growth intelligence for one artist
```

A missing result may mean:

```text
the entity exists
but this intelligence result is unavailable
```

The frontend should therefore show an unavailable-intelligence state rather than assuming the entire entity does not exist.

### Frontend Behaviour

The current frontend already distinguishes between states such as:

```text
loading
data available
empty result
intelligence unavailable
API error
connection error
```

This prevents an empty analytical result from being displayed as a technical failure.

### Edge-Case Risk

If empty collections were not handled correctly, PMIP could incorrectly show:

```text
server error
broken component
failed dashboard
```

when the real situation is simply:

```text
no intelligence currently available
```

This would make the system misleading for users.

### Consistency Finding

The current PMIP integration handles empty intelligence results correctly.

The clearest confirmed example is:

```text
Market Movements
```

where the latest intelligence run contains no movement rows but the API and frontend still behave normally.

This confirms that the system can distinguish between:

```text
empty intelligence
```

and:

```text
failed intelligence request
```

### Empty Intelligence Review Result

```text
Current Status: PASS
```

Empty intelligence tables or empty latest-run results do not cause the PMIP application to fail.

The backend returns a valid empty result, and the frontend presents an appropriate empty state.

This behaviour should be preserved as the scheduled intelligence refresh pipeline is introduced.
